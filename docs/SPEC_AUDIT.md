> تنظیمات پورت برای مدیر و Setup استاندارد Windows اضافه شد و مجموعه ۳۰ تست با موفقیت اجرا شد. موارد

تاریخ ممیزی: ۱۴۰۵/۰۶/۲۸  
دامنه: مقایسه‌ی `PROJECT_MASTER.md` با کد و فایل‌های موجود.  
محدودیت: کد تغییر نکرده است. اجرای تست‌ها در این محیط انجام نشد، چون `pytest` نصب نیست؛ بنابراین مواردی که فقط با اجرای واقعی قابل اثبات‌اند، «نیازمند تست» علامت خورده‌اند.

## جمع‌بندی

- پیاده‌سازی موجود یک نمونه‌ی قابل‌توجه از محصول است: Flask، SQLite، اولین ادمین، ورود/خروج، قفل پس از ۵ خطا، مدیریت کاربر، ثبت درآمد/هزینه، حذف نرم، گزارش، لاگ و بکاپ در کد دیده می‌شود.
- وضعیت `PROJECT_MASTER.md` با کد هم‌خوان نیست: بیشتر Micro Taskها هنوز تیک نخورده‌اند، در حالی که بخش زیادی از آن‌ها در سورس پیاده‌سازی شده‌اند.
- تأیید نهایی شبکه، Windows، مرورگر/موبایل، چاپ A4/A5، چندکاربره و Restore روی محیط واقعی انجام نشده است.
- مورد مهم ناقص: تنظیمات بکاپ خودکار در رابط Admin قابل مدیریت نیست و مسیر تنظیم‌شده‌ی `Setting` با فرم بکاپ دستی پوشش داده نشده است.
- مورد مهم مشکوک به خطا: لاگ‌های ورود ناموفق و قفل‌شدن، snapshot کاربر را ثبت می‌کنند اما طبق قرارداد سند مادر، جزئیات کامل‌ترِ رویداد (به‌ویژه فیلدهای جداگانه‌ی نام/نام‌خانوادگی و پیام خطا) یکدست و کامل نیستند.

## انجام‌شده یا عمدتاً پیاده‌سازی‌شده

### زیرساخت و معماری

- Flask به‌عنوان backend و پورت پیش‌فرض ۴۰۰۰ در `run.py` مشخص است.
- سرور روی `0.0.0.0` گوش می‌دهد و با Waitress اجرا می‌شود؛ از نظر کد برای LAN آماده است.
- SQLite در نسخه نصب‌شده داخل `C:\ProgramData\DailyBook\dailybook.db` نگهداری می‌شود؛ foreign key، `busy_timeout` و WAL در `app/__init__.py` فعال‌اند.
- جدول‌های Users، DailyEntries، AuditLogs و Settings در مدل‌ها تعریف شده‌اند و `db.create_all()` اجرا می‌شود.
- Username یکتا است؛ رمز به‌صورت hash ذخیره می‌شود؛ snapshot هویتی ثبت‌ها وجود دارد.
- حذف کاربر و ثبت‌ها نرم است و سوابق ثبت‌ها با `created_by_*_snapshot` حفظ می‌شوند.

### اولین Admin و احراز هویت

- Setup Admin فقط وقتی جدول User خالی است نمایش داده می‌شود.
- نام، نام خانوادگی، Username، Password و تأیید Password وجود دارد.
- Login/Logout، session، CSRF و redirect امنِ `next` پیاده‌سازی شده‌اند.
- Username/Password نادرست، کاربر inactive/deleted و حساب locked کنترل می‌شوند.
- پس از ۵ تلاش ناموفق، حساب قفل و تلاش بعدی رد می‌شود.
- Admin می‌تواند کاربر را فعال/غیرفعال، حذف، unlock و password را reset کند.
- User عادی به مسیرهای Admin دسترسی ندارد و فقط ثبت‌های خودش را می‌بیند/تغییر می‌دهد.

### فرم ثبت و گزارش

- تاریخ شمسی در UI و تبدیل شمسی/میلادی در backend وجود دارد.
- نوع فقط `expense`/`income`، شرح، مبلغ مثبت صحیح و ثبت اجباری کنترل می‌شوند.
- مبلغ با جداکننده‌ی سه‌رقمی و اعداد فارسی نمایش داده می‌شود.
- زمان واقعی ثبت جدا از تاریخ انتخابی ذخیره می‌شود.
- آخرین ۱۰ ثبت همان کاربر نمایش داده می‌شود.
- ویرایش و حذف فقط برای مالک ممکن است؛ حذف نرم و ثبت before/after در لاگ وجود دارد.
- گزارش Admin ستون‌های تاریخ، شرح، بدهکار و بستانکار و جمع هر دو را دارد؛ expense به بدهکار و income به بستانکار می‌رود.
- فیلتر بازه‌ی تاریخ شمسی در مسیر گزارش پیاده‌سازی شده است.

### رابط و Audit

- قالب کلی RTL، فارسی، responsive و دارای CSS چاپ وجود دارد.
- Tab طبیعی HTML، دکمه‌های قابل focus و ثبت فرم با Enter از نظر ساختار پشتیبانی می‌شوند.
- Popup موفقیت، دکمه‌ی «تأیید» و بازگشت focus به شرح وجود دارد.
- صفحه‌ی لاگ فقط برای Admin است و فیلتر رویداد/کاربر، before/after و پاک‌سازی دارد.
- رویدادهای اصلی login، logout، setup، قفل حساب، ایجاد/ویرایش/حذف ثبت، مدیریت کاربر و بکاپ در کد لاگ می‌شوند.

### Backup

- Backup دستی، backup خودکار روزانه، integrity check و fallback به مسیر پیش‌فرض در سرویس بکاپ وجود دارد.
- مسیر پیش‌فرض و اسکریپت‌های PowerShell برای backup/restore موجودند.
- Restore قبل از جایگزینی فایل، فایل SQLite و نتیجه‌ی restore را اعتبارسنجی می‌کند.
- برای مسیر سفارشی نامعتبر، fallback و رویداد لاگ در سرویس پیاده‌سازی شده است.

## ناقص، مغایر یا نیازمند تکمیل کد/مستندات

- بیشتر موارد فازهای ۱ تا ۱۴ در `PROJECT_MASTER.md` هنوز `[ ]` هستند؛ بنابراین آن سند به‌عنوان وضعیت واقعی پروژه به‌روز نیست.
- Micro Task 0.7 (اولین commit با عنوان مشخص) طبق `git status` انجام نشده است.
- Micro Taskهای 0.10 و 0.11 (اجرای localhost و باز شدن از LAN) در وضعیت رسمی تأیید نشده‌اند.
- `Setting.backup_path` و `auto_backup_enabled` در مدل وجود دارند، اما UI برای تغییر تنظیمات خودکار/فعال‌سازی آن‌ها وجود ندارد؛ صفحه‌ی backup فقط backup دستی می‌گیرد.
- backup دستی در `admin.py` تنظیم مسیر را ذخیره نمی‌کند؛ بنابراین «تغییر مسیر Backup» به‌صورت پایدار انجام نمی‌شود.
- هشدار قابل مشاهده برای Admin در صورت fallback/خرابی مسیر در UI مشخص نیست؛ فقط flash نتیجه‌ی عملیات/لاگ وجود دارد.
- چاپ A4/A5 فقط با `window.print()` و CSS media انجام می‌شود؛ انتخاب مستقل A4/A5 و کنترل دقیق صفحه‌بندی/حاشیه‌ها در کد وجود ندارد.
- فیلتر گزارش با ورودی نامعتبر تاریخ، مسیر خطای صریح/تجربه‌شده ندارد و باید با تست UI بررسی شود.
- در گزارش و لاگ، تبدیل کامل همه‌ی اعداد/زمان‌ها به فارسی تضمین نشده است؛ مثلاً timestamp لاگ مستقیماً render می‌شود و فقط عنصر دارای `data-persian-number` به‌صورت client-side تبدیل می‌شود.
- قرارداد Log در همه‌ی مسیرها یکدست نیست: `auth.py` رویدادهای ورود ناموفق را با فیلدهای کلی‌تر ثبت می‌کند و پیام خطا/نتیجه برای همه‌ی رویدادها یکسان نیست؛ رویداد «تعداد تلاش ناموفق» هم به‌عنوان event جداگانه وجود ندارد و در توضیح login_failed ادغام شده است.
- رویدادهای تغییرات entry به eventهای کلی `update_entry`/`soft_delete_entry` متکی‌اند؛ بررسی تفکیکی «تغییر تاریخ، نوع، شرح و مبلغ» در UI لاگ پیاده نشده است.
- صفحه‌ی Users ویرایش مشخصات نام/نام خانوادگی/username را ندارد؛ فقط ایجاد، وضعیت، حذف، unlock و reset password ارائه شده است.
- محدودیت اینکه Admin اصلی تنها Admin قابل مدیریت باشد، در مدل/رابط به‌صورت صریح enforce نشده است.
- تست‌های موجود دامنه‌ی محدودی دارند و تست UI، چاپ، responsive، دسترسی‌پذیری، همزمانی چند کاربر و شبکه را پوشش نمی‌دهند.
- `pytest` در محیط ممیزی موجود نبود؛ بنابراین حتی تست‌های موجود نیز در این نوبت اجرا و تأیید نشده‌اند.

## موارد نیازمند تست واقعی Windows/LAN

این موارد از روی کد قابل اثبات قطعی نیستند و باید روی Windows واقعی، با حداقل یک سرور و چند کلاینت بررسی شوند:

1. ساخت Setup با `BUILD_WINDOWS_SETUP.bat` و سپس Clean Install، Upgrade، Uninstall و اجرای خودکار Windows Service پس از Restart.
2. باز شدن `http://<server-ip>:4000` از یک کامپیوتر دیگر و موبایل در همان LAN.
3. اثر واقعی قانون Windows Firewall ساخته‌شده توسط Setup و به‌روزرسانی آن پس از تغییر پورت.
4. ورود همزمان ۲، ۳ و ۵ کاربر، ثبت همزمان چند رکورد و نبودن تداخل/خطای SQLite.
5. همزمانی Login/Logout، قفل حساب و Unlock توسط Admin از کلاینت دیگر.
6. قطع موقت شبکه هنگام نمایش فرم، ارسال ثبت و اتصال مجدد؛ بررسی عدم ثبت دوباره یا از دست رفتن داده.
7. عملکرد روی مرورگرهای Windows و موبایل، RTL، اعداد فارسی، تقویم/تاریخ شمسی و ترتیب Tab بدون ماوس.
8. Popup موفقیت و برگشت focus به شرح پس از چند ثبت متوالی.
9. Print Preview واقعی و چاپ خوانا روی A4 و A5، شامل چند صفحه، حاشیه، RTL، تاریخ و اعداد فارسی.
10. Backup دستی روی مسیر محلی و مسیر شبکه‌ای، fallback هنگام unavailable شدن مسیر، و قابل‌بازگشت بودن Restore پس از توقف سرویس.
11. Backup خودکار پس از اولین request روزانه، رفتار در Restart و رفتار با مسیر سفارشی نامعتبر.
12. Snapshot نام/نام‌خانوادگی/Username پس از تغییر یا حذف کاربر و صحت نمایش آن در ثبت‌ها و لاگ‌ها.
13. دسترسی مستقیم کاربر عادی به URLهای Admin، مشاهده‌ی ثبت دیگران و تلاش‌های CSRF/URL دست‌کاری‌شده.
14. اجرای `pytest` پس از نصب وابستگی‌های توسعه و ثبت نتیجه‌ی واقعی تست‌های فعلی؛ سپس افزودن/اجرای تست‌های Windows/LAN.

## نتیجه‌ی نهایی

کد فعلی یک پایه‌ی عملیاتی برای MVP ساخته است، اما طبق معیارهای `PROJECT_MASTER.md` هنوز «تحویل نهایی شبکه‌ای» محسوب نمی‌شود. برای اعلام Done باید ابتدا تست‌های واقعی Windows/LAN و چاپ/چندکاربره انجام شوند و سپس تنظیمات backup، ویرایش کاربر و یکدست‌سازی Audit Log تکمیل یا صریحاً از دامنه خارج شوند.
